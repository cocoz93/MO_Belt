# 벨트스크롤 방 서버 — 설계

> 이 문서는 **구현 전에 설계를 고정하려고** 쓴다. 코드가 나온 뒤에 쓰면 이미 뒤집힌 뒤다.
> 결정마다 **왜 그렇게 정했는지**와 **무엇을 버렸는지**를 같이 적는다.
>
> 대상 = `logic.js` 를 C++ 로 옮겨 4인이 한 방에서 때리고 서버가 판정하는 서버.
> 클라(브라우저)는 이미 있다 — 저장소 루트의 `logic.js` · `game.js` · `index.html`.

## 한눈에

```
[클라]  내 캐릭터는 즉각 움직인다        ← 렉이 있어도 안 멈춘다
   │    같은 logic 을 돌려 미리 판정
   ↓    "이 틱에 이 입력을 넣었다" 를 보냄
[서버]  60Hz 고정 틱으로 방을 돌린다
   │    클라가 보낸 판정을 서버 값과 대조
   ↓    어긋나면 서버 값으로 되돌린다 (끊지 않는다)
[클라]  남과 몬스터는 서버 값을 따라간다  ← 여기는 반 박자 늦는다
```

**던파를 모방한다.** 게임 구조(방 · 4인 · 던전 · 정산)는 던파를 따르고, 신뢰 모델만 현대식으로 간다.
던파를 고른 이유는 취향이 아니라 **비대칭이 뚜렷해서**다 — 내 캐릭터는 즉각이고 남은 튄다는 것이
플레이만 해도 눈에 보이고, 그 비대칭이 곧 이 설계의 뼈대다.

## 1. 범위를 먼저 못 박는다

**만드는 것** — 4인이 한 방에 들어가서 때리고, 서버가 판정하고, 정산까지 도는 것.

**일부러 안 만드는 것** — 점프 · 콤보 · 잡기 · 무기 여러 종 · 타격 이펙트 · 화면 흔들림.

전부 손맛을 다듬는 영역이다. 이 선을 넘는 순간 **"서버가 도는가"를 확인하기 전에 게임을 만들고 있게 된다.**
같은 함정에 한 번 빠져 하루를 되돌린 적이 있다(FPS 프로토타입이 액션RPG로 번졌다).

## 2. 왜 이 구조인가 — MMO 서버와 정반대 축

같이 만든 IOCP MMO 서버와 **병목이 반대쪽에 있다.** 그래서 두 개를 나란히 놓는 것이 목적의 절반이다.

| | IOCP MMO | 이 서버 |
|---|---|---|
| 단위 | 하나의 큰 맵 | 방 하나(4인 + 적 10) |
| 병목 | **브로드캐스트 · AOI**, 게임스레드 1개가 천장 | 방이 독립이라 **코어만큼 늘어난다** |
| 늘리는 법 | 맵 샤딩이 필요 — 한 맵을 못 쪼갠다 | 방을 워커에 더 붙이면 된다 |
| 실측 거리 | 동접 천장(~5,000) | **방이 몇 개까지 붙나 · 병목이 어디로 옮겨가나** |

MMO 쪽은 게임스레드 하나가 모든 세션의 시야 계산을 떠안아 코어를 더 줘도 안 늘었다.
이쪽은 **방 사이에 공유 상태가 없다.** 그 차이가 어디까지 가는지가 이 프로젝트로 재려는 것이다.

## 3. 권위 — 클라가 먼저 판정하고 서버가 검증한다

**선택지는 셋이었다.**

```
클라 권위      즉각적이지만 조작을 못 막는다
서버 권위      안전하지만 렉만큼 손이 늦다 — 벨트스크롤에서는 못 쓴다
클라 선판정    ← 이것. 내 캐릭터는 즉각, 남과 몬스터는 서버 값 추종
+ 서버 검증
```

벨트스크롤은 **때리는 맛이 전부**라 입력에서 타격까지 왕복 시간이 끼면 게임이 아니게 된다.
그래서 클라가 자기 캐릭터의 1차 판정자가 된다.

**대신 비대칭이 생긴다.**

- 내가 때리는 것 → 즉각 보인다
- **몬스터가 나를 때리는 것 → 서버 판정이라 반 박자 늦다**

이건 결함이 아니라 던파가 실제로 그렇게 돌고, 사람이 그 지연을 잘 못 느끼는 쪽을 고른 것이다.

**데미지 계산은 서버가 한다.** 클라는 "때렸다"까지만 말한다.
숫자를 클라가 정하면 검증할 것이 남지 않는다.

## 4. 스레드 — 소켓은 소유한 워커만 만진다

```
[epoll 워커 N]   각자 자기 listen 소켓(SO_REUSEPORT)과 자기 epoll 을 갖는다.
                 접속 수락 → recv → 패킷을 뜯어 → 그 방의 입력 큐에 넣는다.
                 **송신도 겸한다** — 표시(dirty)된 세션의 송신링을 비우고,
                 다 못 보내면 자기 epoll 에 EPOLLOUT 을 걸어 뒀다가 마저 보낸다.
[게임 워커 G]    60Hz 고정 틱 → 자기 방들을 순회하며 step() → 스냅샷을 세션 송신링에
                 쓰고 표시만 한다.
[DB 워커]        (자리만 예약) 잡 큐 + 전용 스레드. 정산·저장이 생길 때 채운다.
```

**소켓 하나는 한 워커만 만진다.** 수락도 수신도 송신도 등록 해제도 전부 그 소켓을 소유한
epoll 워커의 일이다. MMO 의 epoll 포팅은 여러 워커가 한 세션을 깨울 수 있어 수신 직렬화
게이트를 덧대야 했는데, 소유를 고정하면 그 게이트들이 **애초에 필요 없어진다.**

**게임 워커는 소켓 syscall 을 한 번도 부르지 않는다.** 이게 이 그림의 핵심이다.
(틱을 기다리는 sleep 도 syscall 이지만 소켓과 무관하니 허용 — 예전의 "syscall 을 한 번도"를
여기서 정밀화했다.)

60Hz 고정 틱이 소켓 이벤트에 흔들리면 안 되므로 **epoll 워커와 겸하지 않는다.**
겸하게 두면 트래픽이 몰릴 때 틱이 밀리고, 그러면 **틱 밀림을 방 부하 지표로 못 쓴다** —
네트워크 탓인지 계산 탓인지 구분이 안 되기 때문이다.

송신 워커를 따로 두지 않는 이유는 11절에 있다. MMO 실측(송신을 게임스레드에서 떼자
틱 p99 39ms → 17ms)의 교훈은 **"게임 워커가 소켓을 만지지 말라"**는 것이고, 그건 위
원칙으로 이미 지켜진다. 송신 표시는 게임 워커가 메모리 비트맵만 세우고 epoll 워커가
1ms 주기로 깨어나 걷어 간다 — 스냅샷이 20Hz 라 1ms 는 티가 안 난다.

## 5. 방과 워커 — 소유권을 고정해 락을 없앤다

**방을 만들 때 가장 한가한 워커에 붙이고, 방이 죽을 때까지 안 옮긴다.**

그러면 **방 하나를 건드리는 스레드가 언제나 하나뿐**이라 방 안에 락이 없다.
액터 배열도, 입력 큐 소비도, 되감기 고리버퍼도 전부 그 워커 것이다.

**방 목록이 바뀔 때** — 관리자가 「넣을 큐」·「뺄 큐」에만 밀고,
**워커가 틱 경계에서 자기 목록을 스스로 고친다.** 틱을 도는 중에는 목록이 변하지 않는다.

```
관리자 ──push──> [넣을 큐] ──┐
                             ├──> 워커가 틱 시작 전에 자기 목록 갱신
관리자 ──push──> [뺄 큐]  ──┘
```

### `roomId % K` 는 쓰지 않는다

**처음에 그렇게 정했다가 철회했다.** 방은 생겼다 사라지므로,
번호를 K로 나눠 붙이면 **살아있는 방이 한 워커에 쏠린다.** 죽은 방의 자리는 부하가 아니다.

MMO 에서 이미 데인 자리다 — `sessionId % K` 로 송신 워커를 고르다 쏠림이 나서
`uniqueId % K` 로 고쳤다. 같은 실수를 반복하지 않는다.

## 6. 시간 — 틱 하나가 기준

`logic.js` 가 이미 그 규율로 쓰여 있다.

```js
const TICK_HZ = 60;
const TICK_DT = 1 / TICK_HZ;
```

**초가 아니라 틱으로만 센다.** 공격 판정도 「11번째 틱에 맞는다」이지 「0.18초에」가 아니다.

### 틱이 밀리면 — 세 틱까지만 따라잡고, 그 이상은 건너뛴다

처음에는 「무조건 건너뛴다」였다(철회 — 11절). 밀린 만큼 전부 몰아서 돌리면 그 시간에
또 밀려 **눈덩이가 되는 것**은 맞다. 그런데 무조건 건너뛰면 반대쪽이 터진다 — 작은 지터에도
게임 시간이 조금씩 사라져, 멀쩡한 방의 시계가 상시 늦는다.
그래서 **기상 한 번에 최대 3틱까지만 따라잡고**, 그보다 밀렸으면 기준 시각을 지금으로
다시 놓는다(rebase). **건너뛴 틱 수를 방 한계 지표로 센다** — 이건 그대로다.

### 입력이 끊기면

**마지막 입력을 유지하다가 10틱(약 0.17초)이 넘으면 정지시킨다.**
바로 세우면 짧은 끊김에도 캐릭터가 덜컥거리고, 계속 유지하면 끊긴 사람이 벽으로 걸어간다.

구현으로는 **플레이어별 입력 링이 10틱 연속 비면 중립 입력으로 바꾼다** —
유지도 정지도 링 규칙 하나로 처리된다.

### 시계 맞추기 — 여기가 제일 먼저 깨진다

접속할 때 서버 틱을 알려주고 왕복을 몇 번 재서, **클라가 「나는 서버보다 몇 틱 뒤」를 들고 있게** 한다.
스냅샷마다 서버 틱이 실려 오므로 계속 보정된다.

⚠ **이 값이 흔들리면 정상 공격이 조작으로 판정된다.** 검증계에서 가장 먼저 깨지는 자리라
계측 항목에 반드시 넣는다.

## 7. 스냅샷 — 자기완결적으로 만든다

**주기 20Hz(3틱마다) 고정. 델타 압축은 쓰지 않는다.**

델타는 「앞 스냅샷을 받았다」를 전제로 하는데, 그 전제가 **UDP 로 갈 길을 막는다.**
지금 TCP 로 시작하지만 뒤 단계에서 스냅샷만 UDP 보조 회선으로 뺄 생각이라,
**한 장만 봐도 상태가 복원되게** 해두면 그 전환이 공짜가 된다.

방 하나가 액터 14(플레이어 4 + 적 10)라 통째로 보내도 작다. 압축할 이유가 아직 없다.

## 8. 검증과 되감기

### 되감기 — 클라 선판정 때문에 1단계로 올라왔다

클라가 「이 틱에 때렸다」고 말하면 서버는 **그 틱의 상태로 되감아** 판정해야 한다.
지금 위치로 보면, 렉이 있는 사람은 늘 헛치게 된다.

방마다 **최근 몇 틱의 고리버퍼**를 둔다. 방 하나가 작아서(액터 14) 몇십 틱을 들고 있어도 부담이 없다.

### 검증에 실패하면 — 끊지 않는다

```
어긋남 발견 → 서버 값으로 되돌린다 → 횟수만 센다
```

**끊지 않는 이유**: 렉과 조작이 **같은 증상**으로 나타난다.
한 번 어긋났다고 끊으면 지하철에서 하는 사람이 전부 튕긴다.

먼저 잴 것은 **「정상 플레이에서 몇 번 걸리나」의 분포**다.
그 분포를 모르는 채로 임계값을 정하면 그 숫자에 근거가 없다.

### 로직 일치(해시 대조)는 1급이다

클라와 서버가 **같은 계산**을 해야 「이 정도는 렉, 이 이상은 조작」을 가를 수 있다.
둘이 미세하게 어긋나면 정상 플레이가 계속 걸린다.

그래서 `logic.js` 에 규칙이 있다.

- `Math.random` · `Date` · `document` · `window` 금지
- 실수는 C++ 로 옮길 때 **반드시 `double`** — `float` 를 쓰면 결과가 갈린다
- 같은 입력을 넣으면 **몇 번을 돌려도 같은 상태**가 나와야 한다

**검증 방법** — 같은 입력열을 양쪽에 먹이고 매 틱 상태 해시를 비교한다. 어긋나는 첫 틱을 찾는다.

## 9. `logic.js` 가 그대로 서버가 된다

클라 코드가 한 줄도 안 섞여 있어서, 이 파일이 곧 서버의 게임 규칙이다.
C++ 로 옮길 때 **값을 다시 정하지 않는다** — 아래는 이미 손으로 맞춰본 실측값이다.

> ⚠ **`game.js` 는 미리보기용 렌더다.** 규칙이 화면에서 어떻게 보이는지 확인하려고 만든 것이지
> 최종 클라가 아니다. 판정·좌표는 전부 `logic.js` 가 정하고, `game.js` 는 그 결과를 그리기만 한다.
> **서버 설계에서 `game.js` 를 근거로 삼지 말 것** — 거기 있는 잔상·번쩍임·화면 흔들림은
> 로직이 모르는 화면 사정이고, 서버로 가지 않는다.

| 상수 | 값 | 무엇 |
|---|---|---|
| `TICK_HZ` | 60 | 고정 틱 |
| `WORLD_W` / `DEPTH_MIN` / `DEPTH_MAX` | 1600 / 0 / 165 | 방 크기(가로 · 깊이 앞뒤) |
| `P_SPEED_X` / `P_SPEED_Y` | 215 / 132 | 플레이어 속도(좌우 · 깊이) |
| `E_SPEED_X` / `E_SPEED_Y` | 98 / 62 | 적 속도 |
| `BODY_HALF_W` / `BODY_HALF_D` | 17 / 9 | 몸 반지름(밀어내기용) |
| `ATK_TICKS` / `ATK_HIT_TICK` | 18 / 7 | 공격 모션 길이 / **맞는 틱** |
| `ATK_RANGE` / `ATK_BACK` / `ATK_DEPTH` | 64 / 8 / 26 | 사거리 / 등 뒤 여유 / 깊이 허용 오차 |
| `ATK_COOLDOWN` | 4 | 다음 공격까지 |
| `HURT_TICKS` / `KNOCK_X` / `DEATH_TICKS` | 12 / 12 / 20 | 경직 / 넉백 / 사망 모션 |
| `E_ATK_RANGE` / `E_ATK_DEPTH` / `E_THINK_GAP` | 52 / 22 / 70 | 적 사거리 · 깊이 · 공격 시도 간격 |

**어설트**(`SKILL` 묶음) — 목표를 골라 지나쳐서까지 파고들며 지나치는 적을 전부 벤다.

| 상수 | 값 | 무엇 |
|---|---|---|
| `ticks` / `blinkTicks` | 24 / 10 | 모션 길이 / **이 안에 도착한다** |
| `searchRange` / `searchDepth` | 720 / 40 | 목표를 고르는 범위(가로 · 깊이) |
| `passBy` | 90 | 목표를 **지나쳐서** 서는 거리 |
| `minDist` / `defaultDist` | 340 / 340 | 최소 전진 거리 / 목표 없을 때 거리 |
| `range` / `depth` | 50 / 30 | 지나가며 베는 앞쪽 거리 · 깊이 |
| `dmg` / `knock` | 2 / 20 | 데미지 / 넉백 |
| `cooldown` | **0** | ⚠ **시험 중이라 0 이다. 원래 값 240(4초)** |

⚠ **모션 길이 셋(`ATK_TICKS` · `HURT_TICKS` · `DEATH_TICKS`)은 `game.js` 의 프레임당 틱과 짝이다.**
`공격 6프레임 × 3틱 = 18` · `경직 4 × 3 = 12` · `사망 4 × 5 = 20`.
한쪽만 고치면 모션이 중간에 잘리거나 늘어진다. **서버로 옮길 때는 이 값만 가져가면 되고 프레임 수는 클라 사정이다.**

**옮길 함수**
`createWorld` · `makeActor` · `step(w, input)` · `setState` · `canAct` · `separate`
· `resolveHit` · `findAssaultTarget` · `resolveDash` · `clamp`(C++ 은 `std::clamp`)

상태는 **여섯**(`IDLE` `WALK` `ATTACK` `HURT` `DEAD` `SKILL`), 종류는 둘(`PLAYER` `ORC`).
입력은 `{ mx, my, attack, skill }` — 전부 `-1|0|1` 아니면 `bool` 이다.

액터가 들고 다니는 것 중 **판정에 쓰이는 것**: `hitDone`(이번 공격에서 판정을 냈나) ·
`hitIds`(어설트 한 번에 이미 벤 상대) · `cool` / `skillCool` · `dashFrom` / `dashTo` · `lastSkillHit`.

### 값을 만지다 데인 것 다섯

**① 넉백은 사거리보다 훨씬 짧아야 한다** (30 → 12).
크게 잡으면 때릴 때마다 상대가 사거리 밖으로 밀려나 **연타가 끊긴다.**

**② 경직 중에는 무적이어야 한다.**
안 그러면 적 여럿에게 둘러싸였을 때 경직이 겹쳐 손도 못 쓰고 죽는다.
`ATK_BACK`(등 뒤로 8) 도 같은 계열이다 — 딱 붙었을 때 헛치는 것을 막는다.
⚠ 다만 **어설트는 예외로 경직 중인 상대도 벤다.** 지나가며 훑는 기술이라 그래야 관통이 성립한다.

**③ 빠른 이동은 점이 아니라 선으로 판정한다** (터널링).
어설트는 한 틱에 30~45px 을 건너뛰는데 몸통 반지름이 17 이라, 지금 자리만 보면
**바로 앞의 적을 통째로 뛰어넘는다.** 실제로 5마리 중 1마리가 안 맞았다.
`resolveDash(w, caster, fromX)` 가 **출발점~칼끝 구간 전체**를 훑는 이유다.
→ 서버가 검증할 때도 점이 아니라 **선**을 봐야 한다.

**④ 파고드는 중에는 밀어내기에서 뺀다.**
`separate` 는 겹침이 **적은** 축으로 미는데, 몸 한가운데를 정면으로 통과하면 가로 겹침이
최대(34)가 되어 "덜 파고든 축"이 **깊이**가 된다. 그래서 **뚫을수록 위아래로 튕겼다**(실측 10.7px).
통과하는 기술이니 겹쳐도 된다 — `ST_SKILL` 이면 밀어내기를 건너뛴다.
`passBy`(90)가 몸통 지름(34)보다 큰 것도 같은 이유다. 끝나는 순간 겹쳐 있으면 그때 튕긴다.

**⑤ 목표 선택에는 동점 규칙이 있어야 한다.**
`findAssaultTarget` 은 거리가 같으면 **`id` 가 작은 쪽**을 고른다.
이 규칙이 없으면 배열 순서에 따라 클라와 서버가 **다른 목표를 골라 위치가 통째로 어긋난다.**
→ 8절의 해시 대조에서 제일 먼저 깨질 자리다.

## 10. 가져다 쓰는 것

IOCP MMO 서버(`MyGit/MMO` — main 병합됨, 서버 디렉토리는 `IOCP_Server` 에서 `MMOServer` 로
개명)에서 이미 돌고 있는 것들이다. 새로 짜지 않는다.

| 무엇 | 어디 | 왜 |
|---|---|---|
| `RingBuffer.h` | `Shared/` | 세션별 송수신 버퍼. 복사하면서 `<new>` include 와 Init 재호출 방어를 더한다 |
| `MonitorManager.h` 의 구조 | `MMOServer/MMOServer/` | 원자 카운터 · 틱 묶음 반영 같은 **계측 구조만**. 플랫폼 의존은 리눅스 전용 정의 4줄로 대체 |
| `relay.js` | `WebClient/` | WS ↔ TCP 릴레이. 43줄, 프로토콜 무관 — 파일째 |
| 양자화 반올림 계약 | `Shared/Protocol/Protocol.h` | **+0.5 반올림**(절삭이면 왕복마다 좌표가 한쪽으로 민다)이라는 계약만. 함수는 눈금이 달라 새로 쓴다 |
| 세션 참조수 규약 | `MMOServer/MMOServer/IOCPServer.cpp` | 「0이면 획득 실패 · 종료 유도 먼저, 반환은 나중」 |

⚠ **`CIOCPServer` 는 물론 `NetIoModel.h` · `Transport_Epoll.cpp` 도 안 가져온다**(11절) —
별칭 한 줄과 멤버 구현이라 몸통 없이는 못 떼어낸다.

**플랫폼** — 리눅스 epoll, WSL2 Ubuntu 24.04 (커널 6.18 · g++-13 · 코어 20 · 메모리 15GB).

**메모리 배치** — 방 하나가 액터 14라 **1KB 남짓이고 통째로 L1 에 들어간다.**
워커별로 자기 방들을 연속 배열에 둔다. SoA 는 이 크기에서 이득이 없어 쓰지 않는다.

**프로세스는 하나.** 로비 없이 「빈자리 있는 방에 자동 배정」만 한다.
다만 **방이 서로 독립이라 나중에 프로세스를 늘리는 것이 그냥 된다** —
MMO 가 한 맵을 못 쪼개 막힌 것과 정반대라, 이 대비는 문서에 남길 값이 있다.

## 11. 철회한 결정 — 되풀이 금지

여기 적힌 것은 **한 번 정했다가 뒤집은 것**이다. 다시 꺼내지 않으려고 남긴다.

| 버린 것 | 왜 |
|---|---|
| ~~`roomId % K` 로 방 배정~~ | 방이 생겼다 사라져 **살아있는 방이 한 워커에 쏠린다**. MMO `sessionId % K` 에서 이미 데임 |
| ~~1단계는 송신 워커를 분리하지 않는다~~ | 송신 워커 풀이 **이미 있다**. 안 쓰는 게 오히려 떼어내는 작업이 된다 |
| ~~1단계는 클라 예측 없이 간다~~ | 던파 모방(클라 선판정)으로 정하면서 **클라가 1차 판정자**가 됐다. 예측이 전제다 |
| ~~해시 대조는 회귀 테스트 수준으로 충분~~ | 위 선회로 **1급**이 됐다. 로직이 어긋나면 검증 자체가 성립하지 않는다 |
| ~~`CIOCPServer` 재사용~~ | 리눅스행이라 안 맞는다 → `NetIoModel` 추상화 재사용으로 대체 |
| ~~`NetIoModel` 추상화 재사용~~ | 실물을 보니 **별칭 한 줄**(`using NetIoModel = CIOCPServer`)이고 `Transport_Epoll.cpp` 518줄도 전부 `CIOCPServer::` 멤버 — 몸통을 버리면 같이 사라진다. 재사용 목록에서 제외 |
| ~~송신 워커 분리~~ (재철회) | 분리의 전제가 「풀이 이미 있다」였는데 위 철회로 소멸. 대신 **소켓 단일 소유**(epoll 워커가 송신 겸직)가 동시 접근 게이트류를 원천 제거한다. "게임 워커는 소켓을 안 만진다"는 원칙은 그대로다(4절) |
| ~~틱이 밀리면 무조건 건너뛴다~~ | 작은 지터에도 게임 시간이 상시 유실된다. **기상당 3틱까지 따라잡고 초과분만 rebase + 건너뜀 계측**으로 교체(6절) |

⭐ 처음 다섯 중 셋이 **「클라 선판정으로 선회」 한 번에 딸려 뒤집혔다.**
권위 모델이 바뀌면 그 아래가 전부 흔들린다는 뜻이라, 이걸 1번으로 못 박은 것이다.

## 12. 아직 안 정한 것

**던전이 방 하나인가, 3개쯤 이어지는가.**

던파는 방 여러 개 + 보스방이다. 1단계는 방 하나를 권했지만 결정은 미뤘다.

방 이동 자체는 구조가 이미 된다 — 「지금 방을 지우고 새 방을 같은 워커에」 라서.
다만 **이동할 때 워커 부하가 출렁여** 실측이 흔들린다. 방 개수를 재는 것이 목적인데
그 값이 방 이동 때문에 튀면 판독이 어려워진다.

**프로토콜 패킷 목록 · 계측 항목 · 빌드 구성**은 MMO 것을 따라가면 되는 것이라 여기서 정하지 않는다.

**부하 도구**는 뒤로 미뤘다. 다만 **없으면 아무것도 못 재므로 1급 항목인 것은 맞다** —
「방이 몇 개까지 붙나」가 이 프로젝트의 실측 거리인데, 그걸 재려면 방을 채울 도구가 먼저 있어야 한다.

## 13. 단계

```
① logic.js → C++ 이식 + 해시 대조     같은 입력에 같은 상태가 나오는지부터
② 방 / 워커 틱                        60Hz 고정 틱, 방 소유권 고정
③ 접속 · 입장                         수용 → 빈 방 배정 → 스냅샷 흐르기
④ 검증 · 되감기                       고리버퍼, 어긋남 되돌리기, 횟수 분포
⑤ 클라를 실제 소켓에                  game.js 는 거의 안 바뀐다
```

**①이 먼저인 이유** — 로직이 어긋난 채로 ④까지 가면 **검증이 걸리는 게 조작 탓인지
계산이 갈린 탓인지 구분할 수 없다.** 그때 되돌아오면 ②~④를 다시 만져야 한다.
